> **In one line:** Conditional HTTP requests using ETags allow servers to return 304 Not Modified, saving 100% of body transfer bytes.

## The idea

When a cached asset expires (or when an asset uses `Cache-Control: no-cache`), the browser does not need to blindly download the entire file again. Instead, it performs a conditional HTTP request to verify whether its cached copy is still valid.

HTTP revalidation operates using validation tokens:
1. ETags (Entity Tags): A unique cryptographic hash or version string generated by the server representing the exact contents of the resource (e.g. `ETag: "68c4e-182f"`). When revalidating, the browser sends the token in the `If-None-Match` request header.
2. Last-Modified: A timestamp indicating when the resource was last altered on the server (e.g. `Last-Modified: Mon, 15 Nov 2026 12:00:00 GMT`). When revalidating, the browser sends `If-Modified-Since`.

If the server checks the hash and determines the asset has not changed, it immediately returns an HTTP `304 Not Modified` response with an empty body! The browser instantly uses its local copy, saving 100% of the payload download bytes.

## See it

```text
// Initial Request & Response:
Client -> GET /index.html
Server <- HTTP 200 OK
          ETag: "abc-789"
          Cache-Control: no-cache
          (Transfers 45 KB HTML body)

// Subsequent Revalidation Request:
Client -> GET /index.html
          If-None-Match: "abc-789"
Server <- HTTP 304 Not Modified
          ETag: "abc-789"
          (Transfers ZERO body bytes; browser uses local cached HTML!)
```

> **Tip:** An HTTP 304 Not Modified response transfers only headers, saving 100% of the response body bandwidth.

## Go deeper
Conditional HTTP requests leverage ETags (Entity Tags) and Last-Modified headers to verify whether cached assets remain valid. When content is unchanged, the server responds with a lightweight `304 Not Modified` status containing zero body bytes, saving 100% of payload transfer bandwidth.


Comparing Strong ETags, Weak ETags, and Last-Modified validators:

| Validator Type | Header Syntax | Comparison Rule | Accuracy |
|---|---|---|---|
| **Strong ETag** | `ETag: "xyz123"` | Exact byte-for-byte binary equality | Highest: safe for byte-range requests |
| **Weak ETag** | `ETag: W/"xyz123"` | Semantically equivalent content | High: ignores minor header/whitespace diffs |
| **Last-Modified** | `Last-Modified: <date>` | Timestamp comparison (1s resolution) | Moderate: 1-second clock granularity |

## Watch out

- Generating dynamic random ETags on every request, completely breaking 304 revalidation.
- Misconfiguring load-balanced multi-server clusters so each server computes differing ETags for identical files.

## Remember

- ETags provide unique version hashes for resources to enable conditional HTTP revalidation.
- The browser sends If-None-Match; if unchanged, the server returns 304 Not Modified with an empty body.
- HTTP 304 revalidation saves bandwidth while guaranteeing users always receive fresh content.
